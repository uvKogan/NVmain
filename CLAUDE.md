1. [cite_start]**Memory Deallocation Fix**: In `FlipNWrite.cpp` (line 265), the code correctly uses `delete modifyCount;` instead of `delete [] modifyCount;` to fix a fatal array deallocation mismatch[cite: 36, 168]. Do not change this back.

3. **Negative Activate-Energy Clamp**: In `src/SubArray.cpp`'s `Activate()`, the DRAM-model energy formula `(EIDD0*tRC) - (EIDD3N*tRAS + EIDD2N*tRP)` assumes `EIDD0` (one-bank activate-precharge current) exceeds the `tRAS`/`tRP`-weighted background current. Real hynix/Micron DDR5-4800 datasheet values invert this (e.g. hynix `EIDD0=60.2 < EIDD3N=117.6`), which yields a negative incremental activate energy - physically impossible. The per-activate delta (`actDelta`) is clamped at `0.0` before being added to `subArrayEnergy`/`activeEnergy`. Documented in `results/cycle6c_ddr5_calibration_and_provenance_report.md` and MBMM_Book_Typst's Project_Book.typ §3.1.6 item (8). Do not revert.

5. **T1.4, Start-Gap wear-leveling decoder (2026-09-18)**: new `Decoders/StartGap/{StartGap.h,StartGap.cpp,SConscript}`, registered as `"StartGap"` in `Decoders/DecoderFactory.cpp` (include plus one `else if`). A faithful re-implementation of Qureshi et al., MICRO 2009 Fig. 4 (Start-Gap wear leveling): `N` logical (data) lines map onto `N+1` physical lines via two shared static registers, `START` (0..N-1) and `GAP` (0..N); `Remap`: `s=(LA+START) mod N`, `PA=(s<GAP)?s:s+1`; `Unmap` (`ReverseTranslate`'s inverse): `s=(PA<GAP)?PA:PA-1`, `LA=(s+N-START) mod N`, with `PA==GAP` (never real data, only possible from a synthesized ACT/PRE/REF that races the live gap position) defensively returning `(GAP-START+N) mod N` instead of crashing. `GapMove`, one step per `StartGapInterval` writes (default 100): `GAP>0 -> GAP--`; else `GAP=N, START=(START+1) mod N`. `N = lines - 1`, `lines = StartGapRegionBytes/64` (default: `ROWS*COLS*64*BANKS*RANKS`, i.e. the channel's full capacity); a logical/physical line `>= N` (the region's one spare byte-line, or anything past the region) passes through unmapped and counts `startGapOutOfRegion`. All state (`START`, `GAP`, `writesSinceMove`, `lines`, plus the three stats) is `static`, shared across the six decoder instances the factory creates (channel, on-chip bus, off-chip bus, rank, bank, plus `MemoryController`'s own); `SetConfig` only derives `lines`/seeds `GAP=N,START=0` once (`if(lines==0)`), idempotent across the six `SetConfig` calls. Write hook: `StartGap::NoteWrite()` in `MemControl/FRFCFS/FRFCFS.cpp::IssueCommand` for WRITE/WRITE_PRECHARGE, guarded by a `bool useStartGap` cached in `FRFCFS::SetConfig` from `Decoder == "StartGap"` (added to `FRFCFS.h`) so there is no per-request string compare; called after `Enqueue()` fixes the request's row/col via the *current* `START`/`GAP`, so a write never sees the gap move it itself triggers. New stats `startGapMoves`, `startGapWrites`, `startGapOutOfRegion`, `startGapBoundaryAlias` (all `ncounter_t`, `RegisterStats()`). Gap-move data traffic (the read+write NVMain would need to physically relocate the line the gap steps over) is **not** modeled; only `startGapMoves` is counted (T5.2 follow-up).

   **Design history**: the task brief's original formula (`PA=(LA+GAP) mod (N+1)`, collapsing `PA==N` to `0`) was checked with a 10-line bijection script before any code was written and found *not* to be a bijection (`Unmap(Remap(x))!=x` for every `GAP!=0`; two logical lines collide on physical slot 0 whenever the brief's collapse rule fires) -- work stopped and was reported BLOCKED rather than improvised past. The Lead ruled a corrected, faithful Start-Gap design (above), which was re-verified for bijectivity before implementation: exhaustive over every `(GAP,START)` pair at `N=5,6,7` and a 137x23-combination spot-check (every `GAP` step, 23 `START` values including both endpoints, full `LA` range each) at `N=131071` -- 0 problems in all cases. **Known, disclosed limitation**: this bijectivity holds only over the logical data range `LA` in `[0,N)`; the single boundary/out-of-region line (`LA==N`, physical `PA==N`) does *not* round-trip through `Unmap` (a 8-line/N=7 exhaustive check over every `(GAP,START)` found `Unmap(Remap(N))!=N` in all 56 combinations tested) because physical slot `N` is *also* a legitimate `Map()` output for real data whenever `GAP<N`, and `Unmap` cannot distinguish the two sources from the bare address alone. This cannot affect wear-leveling correctness (every real data line's `Remap`/`Unmap` pair is exact, per the exhaustive check) or the verification stats (all forward-path-derived), only a `ReverseTranslate`-synthesized ACT/PRE/REF address for that one specific 64-byte line per region; flagged for the Lead rather than silently special-cased further.

   **Review ruling (2026-09-18)**: accepted with visibility rather than redesigned -- with the default whole-channel region the aliased boundary line is the channel's very last physical line, which our traces never touch. Added `startGapBoundaryAlias`: incremented in `Remap()` alongside (in addition to) `startGapOutOfRegion`, but only for the `LA==N` subset (the general `line>N` out-of-region case increments `startGapOutOfRegion` alone). A nonzero `startGapBoundaryAlias` on a given run flags that run's wear numbers as touching the aliased line and is worth a second look before trusting them; documented in the `StartGap.h` header comment alongside the rest of this limitation, along with the stat-semantics note below.

   Verified: `tools/nvmain_regress.sh` PASS x3 (no golden config sets `Decoder`, so all three golden configs are byte-identical to their pre-T1.4 stats). Skew-trace (`documents/MBMM_Book_Typst/research_notes/nvmain_patches/skew.nvt`, `EnduranceModel WordModel`, `EnduranceDist Uniform`, `EnduranceDistMean 1000000`, 1T1R SLC full-DIMM base config, 2,000,000-cycle budget): baseline (no decoder) reconfirms T1.3 exactly, `wearMaxWrites 15936`, `wearHotSpotFactor 233.109`, `wearTotalWrites` sum `19999`. 6. **Upstream defect DELIBERATELY NOT PATCHED - rank `backgroundPower` is per DEVICE in `EnergyModel current` (noted 2026-09-20, MBMM task F1 / final-review C1)**: in `Ranks/StandardRank/StandardRank.cpp`, `StandardRank::CalculateStats()` accumulates `backgroundEnergy` for the WHOLE RANK (every term at lines ~895-941 is multiplied by `deviceCount`), but line ~992 computes `backgroundPower = ( backgroundEnergy / (double)deviceCount * p->Voltage ) / (double)simulationTime / 1000.0` and, unlike `activatePower` / `burstPower` / `refreshPower` (re-multiplied by `deviceCount` at lines ~1015-1017), never multiplies it back. Line ~1021 then adds all four into `totalPower`. **Consequence: in `EnergyModel current` mode the printed rank `backgroundPower` is ONE DEVICE's background power while the rank's activate, burst and refresh are the whole rank's, and the printed rank `totalPower` inherits exactly that omission.** The stats file is internally self-consistent (`totalPower` equals the sum of the four printed components), so no residual or reconciliation check on the stats file alone can detect it. Only the DDR5 configs set `EnergyModel current` (`Config/DDR5_4800_DRAM_subchannel.config`, `DDR5_4800_DRAM_64B.config`, `DDR5_4800_DRAM.config`); PCM uses `energy` and every ReRAM config `NonVolatile`, and both take the else-branch (`backgroundPower = backgroundEnergy / simulationTime`) with no `deviceCount` division at all, so they are unaffected.

   **This is upstream NVMain code from 2014. It is left UNPATCHED on purpose.** Patching the one line would change the printed stats of every DDR5 run, invalidate the golden regression files under `tools/golden/`, and force a full re-simulation and re-record of the frozen 2026-09 datasets. Instead the correction is applied in post-processing, in `process_metrics.py` (see its "CURRENT-MODE BACKGROUND-POWER CORRECTION" section and the `Background_Power_Device_Factor` CSV column), so the raw stats stay exactly what NVMain printed and every derived number is reproducible from the frozen files. Do not "fix" line 992 without a deliberate, documented re-record of the goldens and the datasets.

   **Rule for anyone reading a stats file: never use a rank's `backgroundPower` (or its `totalPower`) raw from an `EnergyModel current` stats file.** Such a file is recognisable by its energy units, `mA*t` instead of `nJ`. Multiply the rank's `backgroundPower` by that rank's device count, `BusWidth / DeviceWidth` from the run's own config (the same arithmetic as `StandardRank.cpp:125`, and the same number NVMain prints as "Creating N banks in all D devices."), before using it or adding it to anything: 4 for `DDR5_4800_DRAM_subchannel`, 8 for `DDR5_4800_DRAM_64B` and the legacy `DDR5_4800_DRAM`. The rank's `backgroundEnergy` counter IS per rank and needs no correction, so `backgroundEnergy * Voltage / elapsed memory cycles / 1000` is an independent way to get the correct rank background power. A quick sanity bound from the config's own currents: module static power cannot be below `devices x EIDD2P0 x Voltage` (0.412 W for the 8-device subchannel DIMM); the uncorrected figure was 0.181 W, below that floor.
